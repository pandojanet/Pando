# How n8n can reach Supabase — four options

Written after the Postgres node couldn't connect. The database is finished and testable
on its own (`supabase/README.md`); this is only about the wire between the two.

The short version: **use option 2.** The other three are here so the choice is informed
rather than the first thing that worked.

---

## The constraint that rules out the obvious answer

Supabase gives every project a direct Postgres host, `db.<ref>.supabase.co`. Since early
2024 that host is **IPv6-only** unless the project pays for the IPv4 add-on. n8n on a
typical VPS has no IPv6 route, so the Postgres node has nothing to dial — the failure
looks like a timeout or "host not found", which reads like a credentials problem and
isn't.

Everything below is a way around that one fact.

---

## Option 1 · Postgres node via the Supavisor pooler

Supabase's connection pooler *is* reachable over IPv4.

```
Host      aws-0-<region>.pooler.supabase.com
Port      5432                  (session mode — we call functions, not single statements)
Database  postgres
User      postgres.<project-ref>
SSL       on
```

**Import:** `n8n/workflows/*.json` unchanged.

| | |
| --- | --- |
| **For** | Two minutes of work. Real SQL, so a query can be pasted from the editor into a node and back. Transactions work, which matters if you ever want two writes to succeed or fail together. |
| **Against** | Another Supabase component in the path. Session mode holds a connection per workflow execution, and the pooler has a connection ceiling — fine at pilot scale, worth watching if crons multiply. Credentials for the database itself live in n8n. |
| **Use it when** | You want SQL in the nodes and the pooler is reachable. |

## Option 2 · HTTP Request → PostgREST RPC  ← recommended

Every write operation takes a single `payload jsonb`, which is exactly PostgREST's RPC
convention:

```
POST https://<ref>.supabase.co/rest/v1/rpc/write_person
apikey: <service-role key>
{ "payload": { … } }
```

**Import:** `n8n/workflows/http/*.json` — the same eight workflows, node for node,
generated by `python n8n/to-http.py`.

| | |
| --- | --- |
| **For** | Works anywhere n8n can make an HTTPS request: no IPv6, no pooler, no database credentials in n8n. The surface is exactly the functions you chose to expose — `admin_read` and the write ops — so a mistake on the canvas can't run arbitrary SQL. Rate limits and logs come free from the API gateway. |
| **Against** | One HTTPS round trip per call, so `admin_write` does a little more network work than a single connection would. No multi-statement transactions across nodes — which is why `write_caregiver_nomination` bundles the nomination and its restricted notes inside one function rather than leaving them to two nodes. Every new database call needs an RPC function; you can't paste ad-hoc SQL into a node. |
| **Use it when** | Almost always, and certainly now. |

**Why the "against" column doesn't hurt us:** the schema was already built as
decision-free operations taking one jsonb, for a different reason (so the canvas holds
the logic). That happens to be exactly what makes RPC work. The only genuinely bundled
write is the one where splitting it would lose a parent's private note.

## Option 3 · The Supabase node

n8n ships a Supabase node with row operations — create, get, update, delete.

| | |
| --- | --- |
| **For** | Credentials are a URL and a key. No SQL to write for simple table work. |
| **Against** | **It cannot call functions.** Every rule this schema puts in a function — the hold, the ladder, the audit row per setter, `admin_read` — would have to be reassembled from raw row writes across several nodes, which is how a nomination ends up stored without its restricted note. It also writes tables directly, so the constraints become the only thing standing between a workflow bug and bad data. |
| **Use it when** | A one-off admin script, never the seed or caregiver paths. |

## Option 4 · Our app proxies the database

Give the Next.js app a Supabase client and have n8n call *our* endpoints.

| | |
| --- | --- |
| **For** | One place holds the service key. Validation and sanitising already live there. |
| **Against** | It inverts the architecture on record: the app talks to n8n, n8n owns persistence (CLAUDE.md, "Working model"). Reversing that means the app needs database credentials, deploys become coupled to schema changes, and the honest `persisted: false` seam — the thing that lets the UI run today with no backend at all — stops meaning anything. |
| **Use it when** | Only if Supabase's REST API is unavailable to you entirely. |

---

## What is already true either way

- **Direction.** browser → our route → n8n → Supabase. Supabase never calls out: no
  database triggers reaching for a webhook, no n8n URL or secret stored in the database.
  Work with no request behind it is a **cron inside n8n**.
- **The service-role key bypasses RLS**, which is why RLS denies `anon` and
  `authenticated` completely (`0004_rls.sql`) and every function is revoked from them.
  Whichever transport you pick, that key is a root password: n8n only.
- **Header Auth on our webhooks** is still needed, and is unrelated to this choice.
  Without it, anyone who learns a webhook URL can write to the database.
- **Switching later is cheap.** `n8n/to-http.py` regenerates the HTTP set from the
  Postgres set, so the two stay behaviourally identical. Edit the Postgres versions,
  re-run it, re-import.

## If you pick option 2, this is the whole setup

1. Run the migrations and `seed.sql` in the SQL editor, then
   `supabase/tests/smoke.sql` — it prints `ALL CHECKS PASSED` and rolls itself back.
2. n8n → Settings → Variables: `SUPABASE_URL = https://<ref>.supabase.co`.
3. n8n → Credentials → Header Auth named `Pando Supabase RPC`: header `apikey`, value =
   the service-role key. (If your gateway also insists on `Authorization`, add
   `Authorization: Bearer <same key>` to the same credential.)
4. Import `n8n/workflows/http/*.json`, activate each.
5. Put the five webhook URLs in `web/.env.local` — one at a time is fine; an unset one
   just means that route still answers `persisted: false`.
