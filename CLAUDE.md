# Pando — project context

Read this first. It is the single place that says what this project is, what state
it is in, and what has already been decided. Keep it current (see the last section).

## What we're building

Pando is an **SMS-first local parenting trust network**: a parent texts a US number
saved as a contact and gets recommendations about local classes, camps, activities
and caregivers, backed by real parents and honestly labelled by source and
freshness. *"AI knows things. Pando knows someone."*

The long-term asset is not the interface — it's the structured **trust + freshness
graph** and the **two-layer matching** on top of it (social affinity × life
relevance). That is what the paid tier sells.

- **Phase 1 — Seed Tool** (what we are building): a mobile-first web app for ~350
  curated founding contributors. Collects the matching profile, activity/place/tip
  recommendations and caregiver nominations. It is *not* a survey — it is the first
  version of the human-truth ingestion layer.
- **Phase 2 — SMS pilot**: the real product. Client folded the old "Phase 3"
  (Twilio + Stripe) into Phase 2 — the channel *is* the product, so it ships with it.

Client: Janet (non-technical, owns product decisions). Agency: QuitCode.

## Working model (why the code looks like this)

**Claude Code writes the app · the developer specifies pages · the app owns the
backend.** So:

- Everything the browser touches is our Next.js app: pages, route handlers,
  validation, sanitising, secrets.
- Business logic is TypeScript in `lib/server/repo/*`, running in the same
  process. `lib/server/db.ts` is the **only** file that knows a connection
  string.
- Unset `DATABASE_URL` ⇒ the route answers `persisted: false` rather than
  pretending. That honesty rule survived the move off n8n and is what makes the
  flow walkable before there is a database.
- Postgres is Supabase, reached over the **pooler** (IPv4). The direct host is
  IPv6-only without the paid add-on and an IPv4 VPS cannot use it — the same
  constraint that once forced an HTTP transport for n8n.
- The n8n instance still runs on the box and still hosts other work; nothing in
  this app talks to it.

## Decisions already made — do not silently revert

| Decision | Why |
| --- | --- |
| **One invite per group — never per parent** (12 Aug) | The middle ground that turned out to be the actual answer. `invites` holds a row per parent group (code, label, optional `market_options.parent_groups` link), an admin manages it at `/admin/invites`, and `people.invite_id` records which one a contributor arrived on. **What that buys:** "which group actually delivered contributors" — arrivals *and* how many of them gave an approved contribution — which one shared link could never answer, and which is half of what QC Answers Q3 wanted. **What it deliberately is not:** a row per person. The day one is, cross-device resume, automatic referral attribution and `/seed/[token]` come with it, and that is the decision below, made twice. **With a database, the table is the only source** (12 Aug): `SEED_INVITE_CODES` is not consulted at all — not even when the table is empty, because a built-in code that works next to a real table is a door no admin opened and no admin can close. That is what took `sgv-founding` out of service. **The consequence to accept:** a fresh deployment with a database and no invites admits nobody by code, exactly as the admin is dark until somebody is added; one invite fixes it. Only an *unreadable* store falls back to the env, and that asymmetry with admin credentials is deliberate: an outage that let a revoked admin in is a security failure, while an outage that made every invite link a dead end takes the tool offline for people who did nothing wrong. Three more rules: the code is a **soft gate**, not authentication; a retired or unknown code **still lets the parent in**, without attribution, because a link forwarded last week must not become a dead end; and `SEED_INVITE_CODES` stays as the fallback so an unconfigured database still admits people. Resolution is cached 60s (`lib/server/invite-cache.ts`) and cleared after any `invite.*` write, because the first thing an admin does after creating a link is open it. |
| **The invite records the group; the profile no longer asks for it** (12 Aug) | "Where this link reached you" (P6) was a question in the tap-first profile. With one invite per group the code already knows the answer, so asking a parent to find their own group in a list was asking them to re-enter a fact we held — and it produced a second, weaker copy of `people.invite_id`. The question is gone, and the two halves it used to mix are now separate: **attribution** is `invited_via_group`, set server-side from the code the server validated; **membership** comes from the "Parent groups" question, where a parent states it themselves. **The invite still writes no affinity edge on its own** — a link forwarded out of a group is evidence somebody shared it, never that whoever opened it belongs there. Asserted in `test:e2e`: a parent who arrives on a group code has the attribution and **no** edge to that group. |

(The *group* half of what Q3 wanted is now covered by the row above, without per-parent links.) **Three consequences are therefore intended behaviour, not gaps:** returning from a second device is impossible (autosave is device-local, so Q4's "jump straight to *add another*" only holds on the same phone), D2 referral attribution stays an admin judgement rather than a URL, and the address stays `/join?i=…` rather than Q2's `/seed/[token]`. So `web/Dockerfile` takes `ARG NEXT_PUBLIC_POSTHOG_KEY` before `RUN npm run build` and `.github/workflows/deploy.yml` passes it from a repo secret. Verified both ways: with the var set at build time the value appears in `.next/static/chunks/*.js`; without it the bundle is clean and the build still succeeds (analytics off, image fine). Changing the key means a redeploy, not a `docker compose up -d`. |

That made the client the author of its own edges: which schools, groups and neighborhoods a parent is connected to, and therefore whose questions reach them and whose answers they see. CLAUDE.md calls that graph the long-term asset, so it was the wrong shape twice — a stale build writes stale weights, and a crafted request can assert an affinity with a school the parent has nothing to do with. **Verified by sending fabricated rows and confirming none survived**, while the real ones derived correctly with weights from the question set. | **No query parameter changes app behaviour** (4 Aug, reversed `?test=1`) | `?i=` and `?src=` are the only ones read, and they are the product's own link. `?test=1` and a short-lived `?reset=1` are gone: a URL that quietly changes what gets stored is a footgun for whoever forwards the link, and the client wants to walk the flow as a parent would. `is_test` stays a column — the schema, payloads and every admin count still filter on it, so a row can be marked from the admin side or by a seed script. **Consequence to accept:** our own walkthroughs now look like real contributors, so clear them from the database rather than relying on a flag. |

| **Admin auth is per person, hashed — the actor is proved, not picked** (10 Aug) | Supersedes "one shared password + pick who you are" (31 Jul), which is what the client asked for and which had one flaw that outweighed its convenience: **every `audit_log` row is written from `session.user`, and `session.user` was self-asserted.** Anyone holding the shared password could sign in as Janet, so "the audit trail names a person" did not mean that person proved anything — on the one surface where a decision about a named caregiver has to carry the name of whoever made it. Now one scrypt record per person (`scrypt:N:r:p:salt:hash`) — **in `admin_users`** since 12 Aug, see the row below; no password is stored anywhere, and **the cost parameters live inside each record** so raising them later needs no migration and cannot silently mismatch. `ADMIN_CREDENTIALS` (the same records in an env var, `npm run admin:credential`) and then `ADMIN_PASSWORD` + `ADMIN_USERS` remain as fallbacks in that order — deprecated, announced on the sign-in screen — for one reason only: the deploy that adds credentials must not take the admin dark before the client has generated them. **Two things worth knowing:** an unknown name is hashed against a throwaway salt so response time cannot enumerate who has access (measured: ratio 1.00), and `ADMIN_SESSION_SECRET` should be set in production — with it, rotating one password ends one person's sessions; without it the signing key is derived from the records, so rotating anyone's signs everyone out. Both behaviours are asserted in `npm run test:auth` (45 checks) rather than assumed — an earlier version of that comment claimed the per-person behaviour held in both configurations, and the test proved it did not. |
| **The credential store is a table, and a populated one is authoritative** (12 Aug) | `ADMIN_CREDENTIALS` got the hashing right and the operations wrong: adding a person, rotating a password and removing someone who left were all an env edit plus a redeploy. **Revoking access needed a build**, which is the one operation that must never wait for one. `admin_users` (drizzle `0008`) holds the same scrypt record per person plus the three facts a string could not carry — `active`, `password_changed_at`, `last_sign_in_at` — and `npm run admin:user -- add\|list\|password\|disable\|enable` is the whole interface, each command writing its own `audit_log` row. **Four rules, none of them optional.** (1) *Authoritative:* if the table has anybody in it, the env vars are not read — otherwise a person revoked here walks back in through an `ADMIN_CREDENTIALS` entry nobody remembered to delete. (2) *Bootstrap:* an **empty** table falls through to the env, so the deploy that creates it does not take the admin dark. (3) *Fail closed:* if the store is configured and unreadable, the mode is `unavailable` — no sign-in, no session honoured, and the screen says so; falling back to the env during an outage is exactly how a revoked admin gets their access back, and it would buy nothing, because every admin page reads through the same database. (4) *Cached 60s* (`lib/server/admin-auth.ts`), because `proxy.ts` runs before every admin request and a round trip against the pooler is ~200ms warm, 1.3s cold — so a revocation lands within a minute, and immediately on the next sign-in, which always re-reads. **Deliberately not built:** a page for managing *other* admins. A session that can grant a session is a different security surface, the client asked for one admin and maybe two (QC Answers Q6), and a CLI leaves the change where an operator made it. |
| **The pilot starts on a shared starter password, and that is a dated decision** (12 Aug) | `janet` and `andrii` exist in `admin_users` with the password `pando` — hashed like any other (`scrypt:65536:8:1:…`), never stored or logged in the clear. It took `--insecure-password` to get past the CLI's 12-character floor, and the choice is written into the audit row as `weak_starter_password: true`, so "is the starter password still in place" is answerable months later without asking anyone. **The floor did not move:** the default `add` still refuses a short password, and `/api/admin/password` still requires 12 — the product's own path only goes upward, so the first time either of them changes it in `/admin/account` the weak one is gone for good. **What it costs while it stands:** five guessable characters open every parent's profile, every restricted note about a named caregiver, and the consent file with unmasked phone numbers. | **Against the pooler, round trips are the only cost that matters — so read paths minimise queries, not query complexity** (10 Aug) | Measured, because the admin felt slow and the obvious suspects were all wrong. Indexes were already on every join column; the heaviest admin query added **6ms** to a **~200–250ms** round trip. What actually cost time: (a) opening a connection is **~1300ms** of TLS + auth, and `idle_timeout: 20` threw the pool away between page loads — now 300s; (b) `contributorDetail` ran **11 queries in a `Promise.all`**, which reads like the fast version and is not — on a cold pool it opens eleven sockets and pays the handshake on ten of them. ## Invariants (breaking one is a product-level bug)

1. A caregiver appears in a user-facing answer **only** if `consent_status = consented`
   **and** `active = true`, enforced at the query level.
2. **No minors.** A nomination under 18 is discarded, not stored as pending.
3. Never present public information as human trust. Labels are **verbatim** from the
   spec and read the *source*, never who typed it.
4. A "vouched / validated by a parent" label requires `provenance = parent_submitted`
   **and** a real contributor behind it.
5. Contributor-protection numbers are enforced **in code, never by judgement**:
   monthly cap (3/5/10/20, default 5), hard 48-hour gap, response-rate governor at
   25%/30 days, and (v3.2 §10) at most one freshness ping per contributor per
   month, never on the same day as a blast. **Phase 2**: nothing sends yet, so
   nothing enforces them yet. What exists today is where they go —
   `lib/server/sms.ts` runs opt-out → quiet hours → *frequency* → provider, and
   `monthly_contact_allowance` is captured from the parent (P14) and stored. The
   invariant is that the first code that sends a blast implements the middle step;
   it is listed here so that code cannot be written without meeting it.
6. All outbound SMS goes through one compliant send layer (`lib/server/sms.ts`):
   opt-out → quiet hours 8:00–21:00 PT → frequency → throttle → provider, in that
   order. No raw Twilio calls anywhere, and always via the Messaging
   Service SID.
7. Never log phone numbers, names or free text. Counts and enums only.
8. Free text about a named person is never published verbatim without human review.
9. "Other" answers are not matchable until an admin promotes them into
   `market_options`.
10. One person, one identity, keyed by phone. "Contributor" is a derived status, not
    a second table.
11. **Nothing about a named parent is stored before their phone is verified.** The
    device holds the profile and the cards; the write routes refuse them without a
    confirmed code. `phone_verified` is a server fact read from the verification,
    never a field the client can set.
12. A caregiver's private note — and the reason behind a hesitant "would you hire
    them again" — never leaves the admin surface, in any form.
13. **No contact details for a nominated caregiver are ever collected or stored.**
    The only path in is the invite the nominating parent sends themselves.
14. A caregiver nomination is firsthand-only: the family must have employed them.
    A secondhand one is refused, not stored as a weaker record.

## Where the logic lives

`web/lib/questions.ts` — the profile questionnaire (order, gating, weights, P3–P14).
`web/lib/demand.ts` — D1 routing: what Pando says back to which kind of question.
`web/lib/caregiver-invite.ts` — the message the parent sends themselves (C11).
`web/lib/caregiver-flow.ts` — 2C: the caregiver's own questions (G1–G10), as data.
`web/lib/caregiver-options.ts` — the option lists **both** caregiver surfaces share.
`web/lib/server/repo/caregiver.ts` — 2C: writing a claim, in one transaction.
`web/lib/seed-chat/scripts.ts` — the capture conversations.
`web/lib/derive.ts` — answers → affinity / relevance / pending-option rows. Pure,
                       and run **on the server** by the profile route — the client
                       copy is ignored (see Decisions).
`web/lib/consent.ts` — consent wording + version. Bump the version, never edit text.
`web/lib/sms-templates.ts` — **registered** SMS copy. Verbatim, versioned.
`web/lib/server/sms.ts` — the only outbound SMS path (compliance order lives here).
`web/lib/server/verify.ts` + `gate.ts` — OTP store and the "nothing until verified" gate.
`web/lib/server/extract.ts` — 1.8. The only file that talks to an AI provider.
`web/lib/server/invite.ts` — invite codes → group + market. Table first, env fallback.
`web/lib/admin/auth.ts` — scrypt, sessions and the throttle. Pure: it is *given* the
                       credentials and never asks where they came from.
`web/lib/server/admin-auth.ts` — where they come from: `admin_users` first, env as
                       bootstrap, fail-closed if the store is unreadable. Cached 60s.
`web/scripts/admin-user.mjs` — the only way in or out of that table (`npm run admin:user`).
`web/lib/server/db.ts` — the only file that knows a connection string.
`web/lib/db/schema.ts` — the data model, and every CHECK that encodes an invariant.
`web/lib/server/repo/*` — the backend: profile, cards, completion, admin read/write.
`web/lib/submit.ts` — what the device holds, and the one flush that sends it.
`web/lib/market-options.ts` — the tap lists: runtime table (from the database) in
                       front, **placeholder** Pasadena taxonomy behind it as the
                       fallback and the seed, awaiting Janet's sheet.
`web/lib/use-market-options.ts` — loads that table once per session, client side.
`web/app/api/market/options/route.ts` — serves it (§16.2); `lib/server/market-cache.ts`
                       is the 60s read cache an `option.*` admin write clears.
`web/scripts/import-market-options.mjs` — how that sheet gets in (`npm run options:import`).
`web/components/ui/Screen.tsx` — the app shell (phone + desktop).
`web/components/site/Shell.tsx` — the public-site shell.

Adding a question should touch one data file and nothing else.

## Keeping this file current

Do this **in the same turn** as the change, not later:

1. **New functionality** → update the status table, and add a row to *Decisions* if a
   choice was made that a future session could unknowingly undo.
2. **A client answer or a new document** → reconcile
   [docs/spec-compliance-review.md](docs/spec-compliance-review.md) (matches /
   deviations / open questions) and note the date.
3. **A new invariant or a new safety rule** → add it to Invariants, and to the
   relevant `.claude/skills/*` if it changes how UI gets built.
4. **A new route, hook or payload** → `web/README.md` (routes table + payload shape)
   and `.env.example`.
5. **Copy changed by the client** in the root `*.html` → port it into `app/(site)/*`
   and record the terminology in Decisions.

Rule of thumb: if the next session would be surprised by it, it belongs here.
