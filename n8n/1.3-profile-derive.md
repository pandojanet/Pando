# n8n scenario — estimate 1.3: profile → affinity derivation (no database)

What to build in n8n. The app is already wired to call it; nothing else in the
codebase needs to change.

**What it does.** Takes the tapped profile and returns the rows that *would* be
written to `social_affinities`, `life_relevance` and `pending_options`, plus the
`people` row that would be upserted. No storage — the point is to get the derivation
rules right and reviewable before Supabase exists.

**What it deliberately does not do:** no AI (derivation is deterministic), no
`adjacent_neighborhood` rows (adjacency is a property of a *pair*, resolved at query
time), no writing of match weights onto rows (weights must stay config —
spec §18.1), no normalising of "other" free text into slugs (that would make
unpromoted values matchable and poison the graph).

---

## 1. Three nodes

| # | Node | Parameters |
| --- | --- | --- |
| 1 | **Webhook** | HTTP Method `POST` · Path `profile-affinity-derivation` · Authentication **None** (for now, see below) · Respond **Using 'Respond to Webhook' node** |
| 2 | **Code** | Mode **Run Once for All Items** · JavaScript · body in §3 |
| 3 | **Respond to Webhook** | Respond With **JSON** · Response Body `{{ JSON.stringify($json.response) }}` · Options → Response Code `{{ $json.status }}` |

Connect 1 → 2 → 3. That's the whole scenario.

URLs on the project's instance:

```
production (workflow Active):  https://n8n-dxmd.srv1576782.hstgr.cloud/webhook/profile-affinity-derivation
test (one call per Execute):   https://n8n-dxmd.srv1576782.hstgr.cloud/webhook-test/profile-affinity-derivation
```

**Why no IF node for validation.** The Code node already knows the rules, so it
returns `status` (200 or 422) alongside the body and the single Respond node uses it.
One less place where a filter expression can silently mis-evaluate.

**Authentication — off today, and that has to change before storage lands.** The app
only sends `X-Pando-Token` when `N8N_WEBHOOK_TOKEN` is set, so leaving both sides
empty works fine. Two things to know while it's open:

- This endpoint echoes back what it was given, including `name` and `phone`. Nothing
  is stored, so there is no data at risk *yet* — but anyone who learns the URL can
  post to it and read their own payload back.
- The moment this workflow writes to a database, an unauthenticated webhook is a way
  for anyone to inject rows into the trust graph — which is the one thing the whole
  product sells. So: add a **Header Auth** credential (header `X-Pando-Token`, any
  long random value) and put the same value in the app's `N8N_WEBHOOK_TOKEN` in the
  same change as the first storage node.

**Also add** (once, for every workflow you build): a separate workflow with an
**Error Trigger** that logs failures somewhere you'll see them.

**What correct output looks like** (this exact code was run against these cases):

| Case | Expected |
| --- | --- |
| the body above | `200` · `would_write: { people: 1, social_affinities: 8, life_relevance: 6, pending_options: 1 }` · `crosscheck.agrees: true` |
| `child_ages: [8, 0, 8]` | collapses to `[0, 8]` → bands `["baby","grade"]` — **two** rows, not three |
| `pasadena-ymca` in clubs **and** parent_groups | **one** `social_group` row, not two |
| `faith: ["prefer_not_to_say"]` | **no** faith row (kept in `answers`, never an edge) |
| `other.schools: ["  Sierra Vista Co-op  "]`, `other.classes: [""]` | one `pending_options` row, trimmed; the empty one dropped |
| no `neighborhood` or no `child_ages` | `422` `{ "ok": false, "error": "neighborhood is required; child_ages is required" }` |
| `phone: null` | `200`, but `person.identity_key_missing: true` — see the gap in §5 |
| `child_ages: [-1]` (expecting) | bands `["expecting","baby"]` |

`crosscheck` compares the workflow's derivation with the app's (`web/lib/derive.ts`).
`agrees: false` means the two sets of rules have drifted — it names exactly which
rows differ, and it is a bug on one of the two sides, not a warning to ignore.

## 3. Code node body

```javascript
// Weights live in config (affinity_weights). Mirrored here only so the response can
// show what a matching query would use — never written onto the row itself.
const WEIGHTS = {
  school: 5,
  activity: 4,
  neighborhood: 3,
  social_group: 3,
  faith_community: 3,
  age_range: 2,
};

const AFFINITY_FIELDS = [
  { field: 'neighborhood',  type: 'neighborhood',    category: 'neighborhoods' },
  { field: 'schools',       type: 'school',          category: 'schools' },
  { field: 'classes',       type: 'activity',        category: 'baby_activities' },
  { field: 'parent_groups', type: 'social_group',    category: 'parent_groups' },
  { field: 'faith',         type: 'faith_community', category: 'worship' },
  { field: 'clubs',         type: 'social_group',    category: 'clubs' },
];

const RELEVANCE_FIELDS = [
  { field: 'budget',        dimension: 'budget' },
  { field: 'logistics',     dimension: 'logistics' },
  { field: 'family_setup',  dimension: 'family_setup' },
  { field: 'trust_circles', dimension: 'trust_circle' },
];

// "None / prefer not to say" is a real answer — the question was seen and declined —
// but it must never become a matchable edge.
const DECLINED = ['prefer_not_to_say'];
const CANONICAL_ID = /^[a-z0-9_-]{1,64}$/i;
const E164 = /^\+[1-9]\d{7,14}$/;

// Age matches as overlapping bands, never exact years. Must stay identical to
// ageBandsOf() in web/lib/questions.ts, or the graph and the UI drift apart.
function ageBands(ages) {
  const bands = [];
  const add = (b) => { if (!bands.includes(b)) bands.push(b); };
  for (const age of ages) {
    if (age === -1) { add('expecting'); add('baby'); }
    else if (age < 1) add('baby');
    else if (age < 3) add('toddler');
    else if (age < 5) add('preschool');
    else if (age < 11) add('grade');
    else if (age < 14) add('tween');
    else add('teen');
  }
  return bands;
}

// Canonical ids only. Anything else is an "other" (handled separately) or junk.
function canonicalIds(value) {
  const list = Array.isArray(value) ? value : value == null ? [] : [value];
  const out = [];
  for (const item of list) {
    if (typeof item !== 'string') continue;
    const id = item.trim();
    if (!CANONICAL_ID.test(id) || DECLINED.includes(id)) continue;
    if (!out.includes(id)) out.push(id);
  }
  return out;
}

const request = $input.first().json;
const payload = request && request.body ? request.body : request;
const answers = (payload && payload.answers) || {};

// ── Validate: the two answers the whole flow requires (spec §8.5) ──────────────
const errors = [];
const neighborhood = canonicalIds(answers.neighborhood)[0] || null;
const childAges = Array.isArray(answers.child_ages)
  ? answers.child_ages
      .filter((n) => Number.isInteger(n) && n >= -1 && n <= 25)
      .filter((n, i, a) => a.indexOf(n) === i)
      .sort((a, b) => a - b)
  : [];

if (!neighborhood) errors.push('neighborhood is required');
if (childAges.length === 0) errors.push('child_ages is required');

if (errors.length > 0) {
  return [{ json: { status: 422, response: { ok: false, error: errors.join('; ') } } }];
}

// ── social_affinities: one row per membership ─────────────────────────────────
const affinityRows = [];
const seenAffinity = [];

function addAffinity(type, value, sourceField) {
  const key = type + '|' + value;
  if (seenAffinity.includes(key)) return;   // clubs and parent_groups can collide
  seenAffinity.push(key);
  affinityRows.push({
    affinity_type: type,
    affinity_value: value,
    source_field: sourceField,
    weight_from_config: WEIGHTS[type] === undefined ? null : WEIGHTS[type],
  });
}

for (const spec of AFFINITY_FIELDS) {
  for (const value of canonicalIds(answers[spec.field])) {
    addAffinity(spec.type, value, spec.field);
  }
}
for (const band of ageBands(childAges)) {
  addAffinity('age_range', band, 'child_ages');
}

// Deliberately absent: adjacent_neighborhood. Adjacency is a property of a PAIR of
// neighborhoods, not of a person's membership — it is resolved at query time from
// neighborhood_adjacency. Pre-expanding it here would double-count against the
// same-neighborhood credit.

// ── life_relevance: posture, never income ────────────────────────────────────
const relevanceRows = [];
const seenRelevance = [];
for (const spec of RELEVANCE_FIELDS) {
  for (const value of canonicalIds(answers[spec.field])) {
    const key = spec.dimension + '|' + value;
    if (seenRelevance.includes(key)) continue;
    seenRelevance.push(key);
    relevanceRows.push({ dimension: spec.dimension, value });
  }
}

// ── pending_options: free text stays unmatchable until an admin promotes it ───
const CATEGORY_BY_FIELD = {};
for (const spec of AFFINITY_FIELDS) CATEGORY_BY_FIELD[spec.field] = spec.category;

const pendingRows = [];
const seenPending = [];
for (const field of Object.keys(answers.other || {})) {
  const entries = answers.other[field];
  if (!Array.isArray(entries)) continue;
  for (const entry of entries) {
    if (typeof entry !== 'string') continue;
    const submitted = entry.trim().slice(0, 80);
    if (!submitted) continue;
    const category = CATEGORY_BY_FIELD[field] || field;
    const key = category + '|' + submitted.toLowerCase();
    if (seenPending.includes(key)) continue;
    seenPending.push(key);
    pendingRows.push({
      market_id: payload.market_id || null,
      category,
      submitted_value: submitted,
      status: 'pending',
    });
  }
}

// ── The person row this would upsert ─────────────────────────────────────────
const phone =
  typeof payload.phone === 'string' && E164.test(payload.phone) ? payload.phone : null;

const person = {
  // Phone is identity. Without it there is no stable key, so a re-delivery of the
  // same payload would create a second person — flagged, not silently accepted.
  identity_key: phone,
  identity_key_missing: phone === null,
  phone,
  name: typeof payload.name === 'string' ? payload.name.trim().slice(0, 60) || null : null,
  market_id: payload.market_id || null,
  neighborhood,
  child_ages: childAges,
  age_bands: ageBands(childAges),
  profile_completeness: Number.isInteger(payload.profile_completeness)
    ? payload.profile_completeness
    : 0,
  source: payload.source || 'direct',
  invite_code: payload.invite_code || null,
  contributor_status: 'pending_founding',
  provenance: 'parent_submitted',
  is_test: false,
  answers,
};

// ── Cross-check against what the app derived ─────────────────────────────────
const clientRows = Array.isArray(payload.social_affinities) ? payload.social_affinities : [];
const clientKeys = clientRows.map((r) => r.affinity_type + '|' + r.affinity_value);
const derivedKeys = affinityRows.map((r) => r.affinity_type + '|' + r.affinity_value);
const onlyInClient = clientKeys.filter((k) => !derivedKeys.includes(k));
const onlyInDerived = derivedKeys.filter((k) => !clientKeys.includes(k));

return [
  {
    json: {
      status: 200,
      response: {
        ok: true,
        // No database in this scenario: the app reports this back verbatim rather
        // than claiming a write happened.
        persisted: false,
        storage: 'none (derive-only scenario)',
        contributor_id: null,
        would_write: {
          people: 1,
          social_affinities: affinityRows.length,
          life_relevance: relevanceRows.length,
          pending_options: pendingRows.length,
        },
        person,
        social_affinities: affinityRows,
        life_relevance: relevanceRows,
        pending_options: pendingRows,
        // Should always agree. If it doesn't, one side's rules changed.
        crosscheck: {
          client_rows: clientRows.length,
          agrees: onlyInClient.length === 0 && onlyInDerived.length === 0,
          only_in_client: onlyInClient,
          only_in_derived: onlyInDerived,
        },
        derived_at: new Date().toISOString(),
      },
    },
  },
];
```

## 4. Point the app at it

`web/.env.local` already holds the line, commented out. Uncomment it **once the
workflow is Active**:

```
N8N_WEBHOOK_PROFILE=https://n8n-dxmd.srv1576782.hstgr.cloud/webhook/profile-affinity-derivation
```

Leave `N8N_WEBHOOK_TOKEN` empty while the webhook has no authentication — the app
omits the header when the variable is empty.

Restart `npm --prefix web run dev` (env is read at startup), then walk
`/join?i=sgv-founding` → profile → **Save my profile**.

What the app does with the response, already implemented in
`web/app/api/seed/profile/route.ts`:

- forwards the sanitised payload with the `X-Pando-Token` header;
- **honours `persisted`** — because this scenario returns `false`, the app keeps
  reporting "not stored" instead of claiming a save (that flag also travels into the
  `seed_profile_saved` analytics event);
- logs `would_write` and `crosscheck.agrees` to the server console — counts and a
  boolean, never rows, so nothing personal is logged;
- a non-2xx or an unreachable workflow ⇒ `502`, and the parent sees "That didn't go
  through. Your answers are safe on this phone — try again."

Two things worth knowing while you build:

- The **test URL** (`/webhook-test/…`) accepts exactly one call per *Execute
  workflow* click. For repeated runs, activate the workflow and use the production
  path.
- Setting `N8N_WEBHOOK_PROFILE` makes the hook **required**. With n8n down, saving a
  profile fails by design. Clear the variable to go back to standalone mode.

## 5. Before this becomes the real thing

**The identity gap.** With no phone we have no stable key, so re-delivery creates a
second person. The payload has no session id to fall back on. Either make the phone
required before the profile saves (product decision), or add a stable `session_id` to
the payload — it already exists in the browser session, it's just not sent. Until
then `identity_key_missing: true` marks the affected records.

**When Supabase arrives**, this scenario becomes a two-node workflow: keep the Code
node exactly as it is, and add one Postgres node before `Respond to Webhook` — the
write itself is one transaction, but every *decision* stays on the canvas:

```sql
select write_person($json::jsonb);
--  1) upsert people on conflict (phone) do update … returning id
--  2) delete from social_affinities where person_id = id;  insert the new rows
--  3) delete from life_relevance     where person_id = id;  insert the new rows
--  4) insert into pending_options … on conflict do nothing
```

Delete-then-insert, not merge: a parent who removes a school from their profile must
lose that edge. Table shapes are in [../docs/n8n-build-plan.md](../docs/n8n-build-plan.md).

**Then this same workflow gets called from three places**, not one — seed profile
save, admin profile edit, and the Phase 2 clarifying-question write-back — because
1.3's job is *re-derivation*, not first-time capture. Build it as a sub-workflow
(`Execute Workflow`) once a second caller appears.

## Changed after you built it (3 Aug 2026)

The client's v3.2 feedback reshaped the questionnaire, so the payload your Code node
receives has new keys. **The node still runs** — it just silently derives fewer rows
than it should (our crosscheck logged `life_relevance: 6` against the app's 10).
Patch it rather than rebuild it.

**`answers.budget` is now an array, not a string.** It was one tap ("Budget posture"),
it is now multi-select ("How do you usually choose a class or camp?"). If the node
does `answers.budget` expecting a string, it now gets `["free_low_cost","value"]`.

**Three new relevance questions**, all arrays, all mapped exactly like `logistics`:

| answers key | `life_relevance.dimension` |
| --- | --- |
| `budget` | `budget` |
| `logistics` | `logistics` |
| `family_structure` | `family_setup` |
| `childcare_now` | `childcare` |
| `trust_circles` | `trust_circle` |

`trust_circles` is a **ranking, never a filter** (client, explicit): store the rows,
weight them first at match time, and always fall through to the best available match.

**One new affinity**, on top of the existing set:

| answers key | `affinity_type` | `score_weight` |
| --- | --- | --- |
| `invite_group` | `social_group` | 3 |

`invite_group` is "which group did this link come from" and can repeat a
`parent_groups` pick — **dedupe on `(affinity_type, affinity_value)`** or that parent
gets a double-weighted edge to their own group. The app already dedupes; the node
must too, since it may be called with a payload the app didn't build.

**New top-level fields to pass through untouched** (no derivation, they are facts):
`first_name`, `last_name`, `phone_verified`, `phone_verified_at`, `sms_consent`,
`wants_founding`, `children` (birth years — see below), `child_ages_at_capture`,
`profile_captured_at`, `monthly_contact_allowance`, `description_consent`,
`topic_preferences`, `invited_via_group`.

**Ages are now birth years.** `children` arrives as
`[{birth_year, expecting, due_year, due_year_precision}]`, with `child_ages_at_capture`
and `profile_captured_at` alongside it. Derive age bands from `birth_year`, not from
the stored age — that is the whole point of the change. `expecting: true` rows have
`birth_year: null` and a `due_year` marked `assumed_capture_year`, so don't treat it
as a known date.

**`topics` and `description` are answer lists too** (`topic_preferences` and
`description_consent` mirror them at the top level). `description` is a consent
control, not a preference: `say_neighborhood` / `say_school_group` / `neither` decide
how Pando may refer to this parent in an answer. `neither` means neither.

**Nothing reaches this webhook before the phone is verified.** The app now holds the
profile on the parent's device until a six-digit code is confirmed
(`SEED_REQUIRE_VERIFICATION=1`, `web/lib/server/gate.ts`), so a payload arriving here
has a verified `phone` — which closes the identity gap noted above. Key on `phone`.
